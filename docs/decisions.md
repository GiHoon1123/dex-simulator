# 설계 결정 기록

원본 Dex-Simulator(NestJS)를 Kotlin·Spring Boot로 옮기면서 내린 결정과 이유를 남긴다. 원본과 동작이 달라지는 곳은 반드시 여기에 적는다.

---

## 0. 원본 분석 (2026-11-10)

- 규모: TypeScript 소스 약 13,200줄(테스트 제외), 테스트 16개 파일 약 5,900줄
- 모듈: `shared`(pool, blockchain, events), `dex-simulation`(market, lp, trader), `mev-simulation`(detector, strategy, bot), `contract-simulation`(router, singleton), `common`(예외 필터)
- 의존 방향: `mev-simulation`과 `common`이 `shared`에 의존. 모듈 사이는 대부분 이벤트로 연결됨
- 이벤트: `trade.executed`, `arbitrage.opportunity`, `market.price.changed`, `transaction.pending/selected/executed/failed`, `block.executing/executed`, `mev.*` 등
- 테스트 범위: dex-simulation(market, lp, trader의 서비스, 컨트롤러, 타입)과 http 예외 필터, 앱 모듈. **shared(pool, blockchain), mev, contract에는 테스트가 없다**
- 숫자: 전부 JS number. `BigInt` 사용 없음. AMM 출력량 계산 `(amountInAfterFee * reserveOut) / (reserveIn + amountInAfterFee)`, 유동성 `Math.sqrt(a * b)` 모두 부동소수점
- 주기 작업과 상태: 블록 생성, 거래 생성기, MEV 봇, 트레이더, 시장 가격이 타이머와 이벤트로 공유 상태를 바꾼다. Node 이벤트 루프 하나라서 락 없이 동작한다

## 1. 기술 스택

- **결정:** Kotlin 최신 안정, JDK 21, Spring Boot 3.x 최신, Spring MVC, 코루틴, JUnit 5 + MockK, ktlint, springdoc-openapi, GitHub Actions
- **이유:** 국내 Kotlin·Spring 공고에서 가장 흔한 조합이다. 주기 작업이 많아서 코루틴이 Kotlin다운 방식이다. WebFlux는 이 프로젝트에 이점이 없다

## 2. API 계약

- **결정:** 원본과 같은 엔드포인트와 JSON 모양 유지
- **이유:** 같은 요청을 양쪽에 보내 결과를 비교할 수 있다
- **예외:** (원본 설계를 바꾼 곳이 생기면 여기에 추가)

## 3. 금액 표현

- **결정:** 토큰 수량과 준비금은 토큰 소수 자릿수에 맞춘 BigDecimal(ETH·WETH·DAI 18, USDC 6, BTC 8, 모르는 토큰 18). 풀 밖으로 나가는 양과 수수료를 뗀 투입량은 최소 단위에서 내림한다. 가격, 비율(%), 신뢰도, USD 추정치 같은 표시용 값은 Double
- **이유:** 자릿수를 고정한 BigDecimal은 최소 단위 정수(wei)와 표현할 수 있는 값이 같다. 정수로 저장하면 JSON 계약(`"amountIn": 1.5`)을 바꿔야 해서 BigDecimal을 골랐다. 내림은 온체인 정수 나눗셈과 같은 방향이고, 반올림 오차가 항상 풀 쪽에 남는다
- **처음 계획과 다른 점:** 처음엔 BigInteger로 적었다. 위 이유로 바꿨다
- **JSON:** 금액은 끝의 0을 지운 일반 숫자로 쓴다(`1000.000000000000000000` → `1000`, `common/json/AmountJson.kt`)
- **원본과 결과가 달라지는 곳:** 스왑 출력과 유동성 계산 결과가 원본의 부동소수점 값과 마지막 자리에서 다르다(예: 1 ETH → 1992.013962 USDC, 원본 1992.0139620...). 출력량이 0이면 원본은 슬리피지가 NaN(JSON null)이었고, 여기서는 0이다

## 4. 동시성 모델

- **결정:** 시뮬레이션 상태는 단일 작성자. 병렬도 1인 코루틴 하나만 상태를 바꾸고, 컨트롤러와 주기 작업은 메시지로 요청한다
- **이유:** Spring MVC는 요청마다 스레드가 다르고 코루틴도 여러 스레드에서 돈다. 원본처럼 공유 상태를 바로 바꾸면 경합이 생긴다. 블록체인도 블록을 순서대로 하나씩 처리하므로 모델이 같고, 테스트가 결정적으로 돈다
- **대안과 버린 이유:** 상태마다 뮤텍스를 두는 방식은 여러 상태를 함께 바꾸는 거래(스왑 → 풀 → 이벤트)에서 락 순서와 범위를 관리해야 해서 단일 작성자보다 복잡하다

## 5. 이벤트 전달

- **결정:** 코루틴 `SharedFlow` 기반 `EventBus`(`common/event/EventBus.kt`). 이벤트 이름(`type`)은 원본과 같다
- **이유:** Spring `ApplicationEventPublisher`는 동기 호출이라, 단일 작성자 스레드에서 발행한 이벤트를 받은 쪽이 다시 시뮬레이션 상태를 요청하면 같은 스레드를 기다리는 구조가 된다. SharedFlow는 발행과 처리를 분리하고, 구독자도 같은 시뮬레이션 스레드에서 돌게 할 수 있다
- **원본과 달라지는 점:** 원본 `emit`은 리스너를 바로 호출했다. 여기서는 발행 순서는 지키지만 처리는 비동기다. 구독자가 없을 때 발행된 이벤트는 버려지므로, 기존 상태가 필요한 구독자는 구독이 열린 직후(`onSubscribed`) 현재 상태를 읽는다
- 원본에 선언만 있고 발행되지 않는 `price.deviation.detected`는 옮기지 않았다

## 7. Spring Boot 버전 (1번 결정 수정)

## 8. 저장소 이름과 원본 처리

- **결정 (2026-11-11 사용자 결정, 실행 완료):** 원본 `Dex-Simulator`를 `Dex-Simulator-nestjs`로 이름을 바꾸고 비공개로 돌렸다. 이 저장소는 `dex-simulator-kotlin`에서 `dex-simulator`로 바꿨다

## 9. shared/pool 이전에서 고친 원본 문제

원본 동작을 그대로 옮기는 것이 원칙이지만, 아래는 명백한 결함이라 고쳤다.

- **DTO 검증이 돌지 않았다:** 원본은 class-validator 규칙을 달았지만 `ValidationPipe`를 등록하지 않아 아무것도 검증하지 않았다. 여기서는 Bean Validation으로 검증하고, 실패하면 400과 `필드: 메시지`를 돌려준다
- **오라클이 풀을 몰랐다:** `registerPool`을 부르는 곳이 없어 가격, TWAP, MEV 탐지가 항상 비어 있었다. 저장된 가격도 준비금에서 다시 읽지 않았다. 여기서는 오라클이 시작할 때 기존 풀을 등록하고, `pool.created`·`pool.updated` 이벤트로 가격을 갱신한다
- **BTC/ETH 외부 가격이 뒤집혀 있었다:** 0.05(ETH당 BTC)였는데 풀 가격은 BTC당 ETH(20)다. 오라클이 동작하면 영구적인 가짜 차익 기회가 생기므로 20으로 바꿨다
- **풀에 없는 토큰으로 스왑할 수 있었다:** tokenA가 아니면 tokenB로 처리했다. 여기서는 `풀에 없는 토큰입니다`로 실패한다
- **준비금이 0 이하가 될 수 있었다:** 0 준비금으로 풀을 만들 수 있었고(가격 계산이 0으로 나눔), 풀 유동성 이상을 뺄 수 있었다. 생성 시 준비금은 0보다 커야 하고, 준비금을 모두 비우는 제거는 `풀 유동성보다 많이 뺄 수 없습니다`로 실패한다
- **같은 주소로 풀을 만들면 덮어썼다:** 409 `이미 존재하는 풀입니다`
- **`POST /pool/system/start`가 아무것도 하지 않았다:** 멈춘 오라클을 다시 시작한다
- **오라클 갱신 주기:** 원본은 시작할 때의 주기를 계속 썼다. 여기서는 매 회차 설정을 다시 읽어 `oracle/config` 변경이 다음 회차부터 반영된다

## 10. shared/blockchain 이전에서 고친 원본 문제

원본 블록체인 모듈은 거래가 풀 상태를 바꾸지 않는 모형(가스만 소모)이다. 이 모형은 그대로 두고, 아래 결함만 고쳤다.

- **풀 스왑이 대기열에 거의 들어가지 못했다:** 풀 모듈이 넣은 임의 nonce(0~999999)를 그대로 써서, 같은 사용자의 두 번째 스왑부터 대부분 "유효하지 않은 논스"로 버려졌다. 변환기가 대기열의 현재 nonce를 쓴다
- **스왑 타입이 `SWAP`이었다:** 원본 타입 값은 `swap`이라 가스 추정이 기본값(200,000)으로 떨어졌다. `swap`으로 넣는다. 그래서 풀 스왑(가스 한도 200,000)은 스왑 추정치(약 300,000)를 넘겨 처음엔 가스 부족으로 실패하고, 한도를 20%씩 올려 다시 들어간다
- **가스 한도 증가가 동작하지 않았다:** 실패한 거래를 다시 넣을 때 오류 메시지를 먼저 지우고 나서 "가스 한도 초과인지"를 확인해, 한도가 오르지 않았다. 지우기 전에 확인한다
- **call data가 가짜였다:** `swap` 인코딩은 선택자 뒤에 0만 붙였고, 디코딩은 임의 주소·임의 금액을 돌려줬다. 실제 ABI(`swap(address,bool,int256,uint160,bytes)`)로 인코딩하고 디코딩한다(`SwapAbi`). 시뮬레이션 사용자 이름(`user-12`)은 주소가 아니라서 SHA-256 앞 20바이트로 만든 고정 가짜 주소로 바꾼다
- **amountSpecified가 소수였다:** 풀 모듈이 `"1.5"`를 넣었다. int256이므로 최소 단위 정수(`1500000000000000000`)로 넣는다
- **거래 생성기의 방향이 토큰과 따로 놀았다:** 입력 토큰과 무관하게 `zeroForOne`을 따로 뽑았다. 입력 토큰에서 정한다
- **거래 생성기가 한 번 실패하면 영원히 멈췄다:** 대기열이 가득 차는 등 예외가 나면 다음 예약을 하지 않으면서 상태는 "실행 중"으로 남았다. 실패를 기록하고 계속 돈다
- **직접 제출 API가 타입을 버리고 시간 기반 nonce를 썼다:** `submit-transaction`이 요청의 type을 거래에 넣지 않았고, nonce를 `Date.now() % 1000000`로 정해 대부분 거절될 수 있었다. 요청 type과 대기열의 현재 nonce를 쓴다
- **블록 해시가 해시가 아니었다:** `"번호-개수-시각"` 문자열을 hex로 바꾼 값이었다. 번호, 이전 해시, 시각, 거래 id에 대한 SHA-256이다
- **가스 가격:** 원본 생성기는 소수 gwei를 만들었다. 정수 gwei로 다룬다
- **블록에 남는 거래 상태:** 원본은 실패한 거래 객체를 다시 대기 상태로 되돌려 블록 안의 기록까지 바뀌었다. 여기서는 블록에 실패 기록(`failed`, 오류)이 남고, 다시 넣는 거래는 새 복사본이다
- **자동 시작:** 원본 `main.ts`처럼 실행하면 자동 블록 생성과 거래 생성기를 켠다(`dex.simulation.auto-start`, 테스트에서는 끔). MEV 봇은 mev-simulation 이전 때 넣는다
- `blockchain-prerequisites.guard`는 MEV 컨트롤러만 쓰므로 mev-simulation 이전 때 옮긴다
